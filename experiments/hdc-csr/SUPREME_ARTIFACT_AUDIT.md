# Kaggle Supreme 8K artifact audit (Go-only, no re-training)

## Why this audit exists

The repository currently contains TWO distinct Kaggle training pipelines:

| Script | Dataset | Loss | Output |
|---|---|---|---|
| root `build_code_graph_brain.py` **current V4** | Synthetic descriptions of 8 software domains (NOT parsed Go AST) | Batch diagonal self-classification cross entropy | `output/knowledge_8k_supreme.bin`, **v2 64-byte header**, `np.packbits()` default **big-endian bit order**, `output/manifest.json`; the script saves **NO trained projection W** |
| `experiments/hdc-csr/kaggle_train_export_real.py` | Actual Go AST manifest texts | MiniLM teacher similarity MSE | `output/real/knowledge_8k_real_ast.bin`, **v2 64-byte header**, **little-endian bit order**, `real_ast_projection.pt`, receipt |

**The root script was updated to V4:** it now trains for a target of 2 hours, writes 10,000 vectors at each 30-minute checkpoint and the end, and produces v2 (64-byte) headers. Unlike a true projection weight checkpoint, `save_checkpoint()` serializes only the **precomputed 8,192-bit vectors**, not `projection_model.state_dict()`. The `manifest.json` has aggregate metadata only: it does not prove the vectors represent real Go AST symbols.

The V4 synthetic output uses **40 blocks of 250 vectors**, with domain `(blockIndex % 8)`. These inferred labels are valid only if the artifact was actually generated by the matching V4 exporter. The domain descriptions are embedded in the training input, so same-domain retrieval is a weak lexical/domain test, not learned program semantics.

Do not conflate the synthetic V4 training job with the separate real-AST trainer. Even if the two binary formats share `MBVM8K1` v2 headers, their text domains, losses and **bit ordering** differ. The binary header has no bit-order field, so the producer convention must be documented separately.

`knowledge_8k_supreme.bin` contains N x 1,024 bytes of precomputed bit vectors, not the original 3,145,728 float32 projection weights. The exact original W cannot be recovered from this index. To embed new Go code identically, a compatible preserved trained projection checkpoint and the MiniLM encoder are both required.

The diagonal cross entropy objective uses each sample's own embedding as its positive (without independent augmented positives, mutation labels, or function-equivalence labels). Its loss may decrease without proving AST functional sensitivity.

## Audit the ACTUAL binary on the VPS

No external dependencies, Python or PyTorch are required:

```sh
go run ./experiments/hdc-csr/cmd/audit_supreme_index \
  -file /path/to/knowledge_8k_supreme.bin \
  -expected-sha256 29d947f45ab120e25ea91630c64a6f55916019d16e7477da5f1019640e154d1b \
  -queries 32 \
  -out supreme_index_audit.json
```

This command does not SSH into your VPS: run it in your repository checkout
**on the VPS**. `-expected-sha256` uses the checksum provided in the
conversation; ideally independently confirm it against the Kaggle upload
and/or authenticated downloaded artifact metadata.

The Go audit (JSON schema `mbvm-index-audit-v2`) strictly validates v1
and v2 headers, declared vector count, file size, dimensions, v2 padding and
optional expected SHA-256. It samples nearest nonself Hamming distances,
counts exact duplicate vectors, bit positions that never vary and observed
fraction of 1 bits.

**Important correction to v1:** `mean_random_pair_hamming` was misleadingly
named. The previous code compared vector `i` with
`(i + N/2 + 1) % N`, so its output (e.g., 2442.4375) depends on node
ordering and is **not** a representative uniformly random-pair mean.
v2 renames this legacy measure to `mean_fixed_offset_pair_hamming`.

**New exact metric:** `mean_all_distinct_pair_hamming_exact` is computed
over ALL unordered distinct pairs without quadratic work. For a dataset
with `N` vectors and `k_j` ones at bit position `j`:

```text
mean_hamming = sum_j [ 2 * k_j * (N - k_j) / (N * (N - 1)) ]
```

This formula counts all disagreements per bit and sums them, giving the
exact global pairwise mean in O(N*8192). It is not a sample.
`mean_marginal_bit_entropy_bits` gives the average per-position binary
entropy; it does **not** measure joint entropy or independence.
A global fraction of one bits close to 0.5 cannot establish maximum
information capacity when bits correlate.

The Hamming scan does NOT need bit-order metadata to calculate distances. The index
header does NOT encode bit endianness, so the tool explicitly reports it
as unknown; do not claim to have inferred `np.packbits` order from the
header. Provenance, source labels and real AST semantics are NOT
derivable from this file.

## Required files for code-semantic mutation evaluation

1. The exact **trained weight checkpoint**, with `proj.weight`
   shape `[8192,384]` and matching normalization conventions.
2. MiniLM sentence embeddings of the five controlled Go-function triples,
   computed with the same text formatting and encoder as training.
3. Independent behavioral labels to evaluate whether
   `d_H(original,functionally_changed)` is greater than
   `d_H(original,equivalent)`.
4. A non-HDC baseline (MiniLM cosine similarity and Go AST mutation
   detection), plus negative controls.

The existing `export_projection_go.py` expects a
`mbvm-projection-8k-v1` checkpoint emitted by the **real-AST** trainer.
It cannot automatically convert a `supreme` index into the trained W.

Do not publish untrusted Kaggle API tokens, private manifest source
code, SSH keys or VPS credentials in the repository or audit output.


## Follow-up structural diagnostic (Go-only)

The v2 audit on the VPS reportedly found ~0.6493 bits of mean marginal
entropy and a 2330.49-bit exact all-pairs mean. These values are determined
by **per-position frequencies**; neither independently establishes
correlation between bit positions nor semantic clustering.

The separate CLI `cmd/audit_supreme_structure` adds:

- Sampled pairwise Pearson/phi association between distinct bit positions,
  comparing observed absolute phi with an approximate independent-column
  reference. This can measure actual positional dependence, but does not
  identify its cause.
- An **opt-in** comparison of within-domain versus across-domain Hamming
  distributions under the V4 **synthetic layout assumption**.
- The fraction of nearest-neighbor queries retrieving the same inferred
  domain compared with the same-domain random-pair baseline.

Run **on the machine that actually holds the index** (not in CI's synthetic
test fixtures):

```sh
go run ./experiments/hdc-csr/cmd/audit_supreme_structure \
  -file /home/ubuntu/mbvm_neural_output/output/knowledge_8k_supreme.bin \
  -expected-sha256 29d947f45ab120e25ea91630c64a6f55916019d16e7477da5f1019640e154d1b \
  -synthetic-v4-layout \
  -column-pairs 512 -domain-pairs 2048 -nearest-queries 32 \
  -out /home/ubuntu/supreme_structure_audit.json
```

Omit `-synthetic-v4-layout` when the producer is uncertain. The CLI will
still test sampled interbit correlations, but will not infer domain labels.
The 8-domain hypothesis is about synthetic software-topic descriptors,
not arbitrary real code or programming intelligence.

## V4 source-block leakage and duplicate controls

The structure audit also reports `block_holdout` when
`-synthetic-v4-layout` is enabled (default 160 sampled queries, adjustable
with `-block-holdout-queries`; 0 disables it).

This stronger check omits **all 250 vectors in the same generation chunk as
the query**, including the query itself and within-chunk near-clones.
It uses every remaining vector as a nearest-neighbor candidate and then
scores the inferred synthetic topic label. A secondary metric excludes
**zero-distance candidates**, including duplicates in other chunks.

The default 160 queries are deterministically spread across the 40 chunks.
For 10,000 vectors, there are exactly 9,750 eligible candidates per query:
1,000 of them come from the four other chunks carrying the same one of
eight synthetic labels. A **uniform random** label-matching baseline is
therefore `1000/9750 = 10.2564%`, not the 12.49% used when only the
query's own vector is excluded.

The report includes cross-block Top1, cross-block nonidentical Top1,
exact-duplicate nearest neighbors, nearest same/other class distances,
margins, and per-domain query/correct counts. A high cross-block score
is evidence of robust topic-template retrieval, **not** validation of Go
behavior semantics.

**Trivial non-neural baseline:** the V4 exporter writes each domain name
and its keyword list *literally* into the input string. A substring
classifier that matches the known eight domain names in those strings
assigns all of them correctly **by construction**. Consequently,
domain-label accuracy without a lexically harder held-out dataset
cannot establish any incremental semantic benefit from HDC.

Recommended command on VPS:

```sh
go run ./experiments/hdc-csr/cmd/audit_supreme_structure \
  -file /home/ubuntu/mbvm_neural_output/output/knowledge_8k_supreme.bin \
  -expected-sha256 29d947f45ab120e25ea91630c64a6f55916019d16e7477da5f1019640e154d1b \
  -synthetic-v4-layout -block-holdout-queries 160 \
  -column-pairs 512 -domain-pairs 2048 -nearest-queries 32 \
  -out /home/ubuntu/supreme_structure_holdout.json
```

This does not require weights W and does not change the current trained
index. It assumes the V4 writer's chunk order is unchanged.

## Direct no-training lexical Top-1 control on the identical 160 V4 queries

The CLI now publishes `lexical_holdout` alongside `block_holdout`
whenever `-synthetic-v4-layout -block-holdout-queries 160` is set.

The lexical control reconstructs V4 source texts from the **exact V4
generator template and eight static domain/keyword tuples**. It tokenizes
the source text into lowercase words, drops numeric ID tokens, computes
Jaccard similarity of unique-token sets, and searches the exact same
9,750 candidate IDs per query, excluding the same 250-symbol source
block. Shared function `blockHoldoutQueryID` guarantees matching query
IDs and domain-balanced coverage across HDC and lexical arms.

**Caution:** this source is reconstructed from the inspected trainer;
neither the bit-vector index nor its checksum cryptographically proves
the producer text. If V4 provenance is wrong, this lexical baseline is
not applicable to the actual index.

The V4 text contains domain name, title and comma-separated domain tags
literally. After removing ID numbers, all source records from one
synthetic domain have identical word sets. Consequently the lexical
baseline is expected to classify **160/160 (100%) by construction**,
even when its source block is excluded. This is not a trained classifier
or a fair latency benchmark, but it establishes that an inexpensive
non-neural text representation is sufficient for this narrow objective.

The observed user-provided HDC result was `156/160 (97.5%)`; a direct
side-by-side report therefore implies **-2.5 percentage points** for
HDC relative to the lexical baseline on domain Top-1, **conditional on
the exact V4 template and reported HDC result**. These are not
measurements of semantic code understanding, retrieval latency or
high-dimensional memory superiority. The neural model might still add
value on a different task, but it needs an independently defined
behavioral benchmark and a saved projection checkpoint W.

A practical next evaluation must obscure domain keywords, hold out
entire template families and test actual unseen Go code against
independently verified behavior labels. These counterfactual
transformations **cannot be embedded by the original model** without
the saved weights W and a compatible MiniLM encoder.
